# 数据模型 — 订单域（order / 回调 / 补单）

> 域文档，从 `运营平台-P1数据模型草案.md` 拆出。P1 第 5 块，数据模型收尾。
> 范围：order（订单）+ order_notify_log（商户回调通知日志）+ 轮询/补单结构（P2/P4 预留）。
> 目标：定清订单主体、三态字段（订单状态/回调/入账）的关系、费率快照、上游回调幂等、超时；与通道域（路由命中费率）、账户域（支付成功触发流水）联动。

最后更新：2026-07-15
状态：⬜ 待评审

---

## 1. 设计原则

1. **订单号三套、各唯一**：`order_no`（平台）、`mch_order_no`（商户）、`channel_order_no`（上游）均建唯一索引，作幂等键。
2. **费率快照**：下单时把命中的商户费率、通道费率（含命中档）快照到订单，并算定 `merchant_fee / channel_cost`；改费率不影响历史单与已生成流水。
3. **三态字段各司其职**：`status`（支付生命周期）/ `callback_status`（是否已通知商户）/ `account_status`（账务视角，是否已入商户账）。详见 §3。
4. **回调幂等**：上游回调按 `channel_order_no` + 状态机乐观锁（`where status=待支付`）防重复入账；商户通知按 `order_no` 重试。
5. **超时**：`expire_at` 来自系统配置「订单支付超时时间(分钟)」；定时任务把过期未支付单置「未出码/支付失败」。
6. **只追加为主**：订单状态可流转（update status），但资金结果一旦入账不可逆，冲正走退款/补偿流水（账户域）。

### 2.3 预留（P2/P4）

- **order_poll_log 轮询日志**（P2）：定时向上游查单的结果记录，对应异常订单「是否记录轮询日志」。
- **补单**（P4）：复用 order 表（`is_reissue=1, reissue_from=原单`）；补单是否需谷歌验证（安全配置开关）。

## 3. 枚举与三态关系

### 3.1 status 订单状态
`待支付 / 支付成功 / 支付失败 / 未出码 / 异常`

### 3.2 callback_status 回调通知
`未通知 / 通知成功 / 通知失败`

### 3.3 account_status 入账状态
`未支付 / 已入账 / 未入账`

### 3.4 三态对应（P1 约定）

| status | account_status | 说明 |
|--------|----------------|------|
| 待支付 | 未支付 | 未成交 |
| 未出码 | 未支付 | 超时/未生成上游单 |
| 支付成功 | 已入账 | 成交且已写商户入账流水 |
| 支付失败 | 未入账 | 失败，未入账 |
| 异常 | 未入账 | 成功但入账/对账异常，待处理 |

> `account_status` 是 `status` 的账务投影，正常同步；仅「支付成功→已入账」存在同事务内的瞬时差。筛选/对账以 `account_status` 为准，列表展示以 `status` 为准。

## 4. 状态机与流程

### 4.1 下单（商户发起）
1. 校验 `mch_order_no` 幂等（同商户不重复）。
2. 通道域路由：按 `pay_method + amount` 筛 `channel_pay_rule` → 按 `poll_weight` 加权随机选启用通道 → 命中 `channel_rate` 档。
3. 快照费率、算定 `merchant_fee / channel_cost`、写 `order`(status=待支付, account_status=未支付, expire_at=now+超时)。
4. 调上游下单 → 回填 `channel_order_no`。

### 4.2 上游回调（支付成功）— 核心，幂等
```
同事务：
  幂等：channel_order_no 唯一 + where status=待支付（乐观锁，防重）
  order.status = 支付成功, account_status = 已入账, pay_time = now
  触发账户域 §4.1 流水：商户入账+M、商户服务费−mf、系统+mf、（通道成本待计费表）
  callback_status = 未通知（异步通知商户）
```
> 失败回调 → status=支付失败；超时未回调 → 定时置 未出码。

### 4.3 商户回调通知（异步）
- 按 `notify_url` POST 结果；成功 → `callback_status=通知成功`；失败 → 重试（写 order_notify_log），`callback_status=通知失败`。
- 「一键回调」= 手动重发通知。

### 4.4 补单 / 超时
- 超时：定时任务扫 `expire_at < now && status=待支付` → 置 未出码（或支付失败，规则待定）。
- 补单（P4）：对异常/丢失单重发起，`is_reissue=1, reissue_from=原单`，走下单+回调流程。

## 5. 查询与统计

### 5.1 列表筛选（14 项，PRD §8.1）
order_no、mch_order_no、channel_order_no、merchant_id、供应商(via channel)、channel_id、通道类型(via channel.type_id)、is_reissue、status、callback_status、account_status、下单时间快捷、时间范围、查询金额（amount 命中）。

### 5.2 当前条件成功率
`列表内容 - 当前条件成功率: x.xx%` = 当前筛选下 `status=支付成功` 单量 / 总单量，**查询时实算**，不落库。

### 5.3 首页/日终口径
- 今日/昨日订单 9 指标：按 `created_at`/`pay_time` + UTC+8 日切聚合。
- 总金额=收单金额（Σ amount），成交额=已支付金额（Σ amount where status=支付成功）。

## 6. 待评审开放点

- **A** `mch_order_no` 唯一性范围：全局唯一还是 `(merchant_id, mch_order_no)` 唯一？（建议后者，不同商户可重号）
- **B** 超时单终态：置「未出码」还是「支付失败」？（影响成功率口径，待产品定）
- **C** `account_status` 是否冗余可去掉、纯由 `status` 推导？（建议保留：账务对账以它为准，且瞬时差需可见）
- **D** 通道成本入账时点（随支付成功 vs 结算时）——联动账户域开放点 E、计费表 B3。
- **E** 订单/流水分库分表预留（高增长表）——联动总览开放点 6、账户域开放点 H。
- **F** 补单与原单的关系：新建 order（is_reissue）还是原单续做？（建议新建+reissue_from 指向原单）
- **G** 商户回调通知重试策略（次数/退避）与「一键回调」权限点。
